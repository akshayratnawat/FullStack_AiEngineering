# Build Plan (step by step)

This follows the "Implementation Sequence" in [architecture.md](architecture.md). It's a learning project, so for every step we: **do one small thing -> explain what and why -> check that it works -> tick the box -> move on.**

Legend: `[ ]` not started, `[~]` files exist but not yet walked through together, `[x]` done and understood.

**Goal:** analysts ask plain-English questions about SEC filings and get answers that cite the exact filing and passage. A wrong but confident answer is worse than no answer, so trust drives the design.

---

## Before step 1 — Accounts and keys

- [ ] **Create a Supabase project and copy its Project URL, anon key and service-role key** (guide: [supabase-setup.md](guides/supabase-setup.md)).
  *Why:* auth and the database both live in Supabase. *You'll learn:* what a project URL / anon key / service-role key are, and why the service-role key must never reach the browser.
- [ ] **Create an OpenAI API key.**
  *Why:* used later for embeddings and answers. Not needed until step 8.
- [ ] **Finish updating `uv`** (`uv self update`; it was blocked by a running process).
  *Why:* the project's `pyproject.toml` uses a setting (`add-bounds`) that the installed uv 0.6.2 doesn't know.

## Step 1 — Scaffold the frontend and backend `[~]`

Files were generated in one go. We'll go back over them one at a time.

- [~] **1a. Backend project** (`backend/pyproject.toml`, `app/main.py`, `app/config.py`, `tests/`).
  *Why:* gives the API a home: a running server with a `/health` check, one place for settings, and a test to prove it works.
  *You'll learn:* what `uv` does, what FastAPI and `pydantic-settings` are, why settings live in one module.
  *Check:* `uv run pytest` passes; `uv run uvicorn app.main:app --reload` then open `/health`.
- [~] **1b. Frontend project** (Vite + React + TypeScript, `package.json`, `vite.config.ts`, `src/`).
  *Why:* the browser app analysts will use.
  *You'll learn:* what Vite, pnpm, TypeScript config and the `@/` import alias do.
  *Check:* `pnpm dev` shows the page; `pnpm tsc --noEmit` and `pnpm lint` pass.
- [ ] **1c. Tailwind CSS (already installed) and shadcn/ui (not yet).**
  *Why:* Tailwind styles the UI; shadcn gives ready-made, accessible components so we don't hand-build buttons and dialogs.
- [ ] **1d. `.env` files from the `.env.example` templates.**
  *Why:* keeps secrets out of git. *You'll learn:* why only `VITE_` variables reach the browser.

## Step 2 — SQLAlchemy models and Alembic setup `[ ]`
*Why:* defines the database schema in code, so the database can be rebuilt and reviewed like any other change. *You'll learn:* ORM models, what a migration is.

## Step 3 — First Alembic migration `[ ]`
*Why:* creates the tables in Supabase: pgvector extension, documents, chunks, full-text column, chats, citations. *You'll learn:* what pgvector and full-text indexes are, why we review autogenerated migrations.

## Step 4 — Supabase Auth in the frontend + token check in FastAPI `[ ]`
*Why:* only logged-in analysts may use the tool, and the backend must verify who is calling before doing any work. *You'll learn:* JWTs, sessions, the anon key versus the service-role key.

## Step 5 — Shared frontend API client `[ ]`
*Why:* one place that adds the backend URL and the login token to every request, with clean error handling. *You'll learn:* `fetch` wrappers, CORS and network errors.

## Step 6 — Chat endpoint with a stubbed reply `[ ]`
*Why:* proves the whole pipe (browser -> auth -> backend -> streamed reply) works before adding AI. *You'll learn:* streaming responses.

## Step 7 — Chat UI on the frontend `[ ]`
*Why:* gives analysts something to type into and see streamed replies. *You'll learn:* the Vercel AI SDK chat hooks, React Router.

## Step 8 — Ingestion: Markdown, chunking, embeddings, writes to Supabase `[ ]`
*Why:* turns downloaded filings into searchable pieces. Answer quality is limited by how clean this step is. *You'll learn:* parsing HTML, chunking, what embeddings are.
*Decision needed first:* how to cite. EDGAR filings have no real pages, so we likely cite by section.

## Step 9 — Semantic search (pgvector) `[ ]`
*Why:* finds passages by meaning, not exact words. *You'll learn:* vector similarity.

## Step 10 — Keyword search + Reciprocal Rank Fusion `[ ]`
*Why:* exact terms matter in finance; combining both searches beats either alone. *You'll learn:* full-text search, rank fusion.

## Step 11 — PydanticAI document agent `[ ]`
*Why:* the LLM answers only from retrieved passages and returns a typed answer plus citations. *You'll learn:* agents, typed outputs, prompt contracts.

## Step 12 — Citation validation and grounding `[ ]`
*Why:* the product's core promise. Code rejects any citation that wasn't retrieved, and the bot says "not enough evidence" when the corpus can't answer. *You'll learn:* how to make trust checkable in code, not just in a prompt.

## Step 13 — Final UI: citations, source passages, empty states, errors `[ ]`
*Why:* lets the analyst verify any claim in one click. *You'll learn:* building a trustworthy UI.
